How tags work

Data Model Change (Layer 1)
// types/index.ts
interface Activity {
  ...
  tags: string[];  // NEW — array of tag strings
}

// DB: stored as JSON text column
ALTER TABLE activities ADD COLUMN tags TEXT DEFAULT '[]';
Migration Strategy
1. Add tags column with default '[]' (no data loss)
2. Existing category_id stays (backwards compat)
3. Auto-populate tags from category name: category "Health" → tags ["health"]
4. Future: deprecate category_id, use tags only
Boundary Contracts Affected
Layer 1→2: Store must read/write tags as JSON
Layer 2→3: ActivityForm adds tag input, EditActivity passes tags

At scale

What breaks with
10 million users

Even with this system. LLMs have limits.

🧠
Context window exhaustion
At 10M users, the codebase is 500K+ lines. The knowledge system is 10K+ lines. Even 1M tokens can't hold it all. The LLM must selectively load context.
Need: Intelligent context retrieval. RAG over the knowledge graph. Load only the relevant subgraph per task.
🔀
Concurrent changes
Multiple agents changing the same files simultaneously. Agent A changes the store while Agent B changes a screen that depends on it. Merge conflicts.
Need: File-level locking. Task dependency DAG. Sequential execution for same-layer changes.
📊
Real user data vs seed data
With 10M users, bugs affect real people. You can't "just revert." Database migrations are irreversible. A/B tests have real statistical power.
Need: Feature flags. Staged rollouts. Automated rollback. Real monitoring (not just sensors).
🤝
Taste and judgment calls
LLMs can't judge: "Is this delightful?" "Does this feel right?" "Will users love or hate this?" Product taste requires human intuition that no amount of context fixes.
Need: Humans for taste decisions. LLMs for execution. Clear boundary between the two.
🌊
Emergent complexity
At scale, dependencies form that nobody designed. Feature A interacts with Feature B in ways neither team predicted. The knowledge graph becomes incomplete by definition (Weinberg's Law).
Need: Observability > documentation. Watch production behavior. The system tells you what's connected by what fails together.

What we still need to build

Gaps in the
current system

🔍
Smart context loader
Instead of reading the entire knowledge system, load only the subgraph relevant to the current task. "I'm changing editActivity" → auto-load its flow map entry + boundary contracts + callers.
🧪
Automated sensors in CI
Today sensors are manual grep commands. They should run automatically on every commit. GitHub Actions checks design tokens, virtual IDs, boundary contracts.
🗺️
Auto-updating flow maps
The Change Flow Map is manually written. It should auto-generate from static analysis (imports, function calls, type usage). Tree-sitter + custom rules.
🔄
Feedback from production
The knowledge system is pre-production. With real users, production errors should auto-add to the Failure Flow Map. "This edge function timed out 50 times" → auto-flag.
🧑‍🤝‍🧑
Human taste layer
A formal interface where the human makes taste decisions and the system records + applies them. Not just CLAUDE.md rules but structured design preferences that agents can query.
📈
Learning from incidents
Every bug should auto-update the knowledge system. "Virtual ID bug in editActivity" → auto-add to Change Flow Map + Failure Flow Map + Sensors. The system gets smarter from every mistake.
