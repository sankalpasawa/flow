Concept 2

Four Flow Maps

Four different ways to see how things connect. Each reveals dependencies the others miss.

📊 Data Flow
Where data is created, transformed, and consumed. User types text → parser extracts fields → store writes to DB → recurrence engine generates virtual instances → screen renders pills.
Reveals: the virtual ID flows from recurrence.ts through the store to every screen. If the ID format changes, everything downstream breaks.
🎯 Decision Flow
Whose intent constrains whose actions. Founder sets vision → Architecture doc constrains what to build → Design spec constrains how it looks → Code implements within those constraints.
Reveals: code should never force a change to the design spec. If it does, the dependency is pointing the wrong way.
💥 Failure Flow
When X fails, what else fails. Edge function fails → Play screen falls back to local HTML. DB write with virtual ID → silent no-op, edit lost with NO error.
Reveals: the most dangerous failures are silent. The virtual ID bug produced no error message — the edit just disappeared.
🔄 Change Flow
When X changes, what else must change. If you change editActivity → check 6 screens that call it. If you change theme.ts → grep every component for the old value.
Reveals: exactly which files to check before committing. This is the map that prevents bugs.

Concept 3

Sensors

Automated checks that detect broken dependencies. Run before every commit. You don't need to map everything — sensors catch problems you didn't predict.

🎨 Design Tokens
Grep for hardcoded hex colors in .tsx files. Zero results = pass.
Before every commit
🆔 Virtual ID Safety
Verify every editActivity caller resolves virtual IDs before calling.
When touching store or screens
📐 Rendering Rules
Check pill/watermark/task filters match the spec in DESIGN.md.
When touching CanvasScreen
🌱 Seed Safety
No INSERT OR REPLACE for activity data. Seeds must not overwrite user edits.
When touching seed files
📝 Theme ↔ Spec
Verify theme.ts values match DESIGN.md spec exactly.
When touching theme or design
🔗 Cross-Layer Check
If change crosses a layer boundary, verify the boundary contract holds.
When any change crosses layers

Real example

The Bug That
Broke Everything

Editing "Morning water" didn't save. Here's how it happened, and how the system would have prevented it.

Without the system
1. Bug report: edit doesn't save
2. Look at editActivity in store
3. Think: "the ID must be wrong"
4. Change the store to strip IDs
5. Break all activity editing
6. Try to fix the fix
7. Break more things
8. Revert everything
9. 45 minutes wasted
With the system
1. Bug report: edit doesn't save
2. Read Change Flow Map for editActivity
3. See: "Virtual ID resolution at CALLER"
4. Check navigateToActivity
5. Find: passes virtual ID to form
6. Fix: one line, extract real ID
7. Run sensors: all pass
8. Done. 5 minutes.

How it works in practice

A Change Flows
Through the System

Say you want to add a new field to Activity (like "energy_level").

1
Identify the layer
Adding a field to Activity = Layer 1 (Data Model). Changes quarterly. High impact.
2
Read the Change Flow Map
"IF YOU CHANGE types/index.ts → CHECK: store, DB functions, every screen that renders Activity, recurrence.ts, seed.ts"
Layer crossing: 1 → 2, 3, 5
3
Change Layer 1: Add the field
Add energy_level to types/index.ts. Add column to DB schema.
types/index.ts, activities.ts (migration)
4
Cross boundary: Layer 1 → Layer 2
Update store to read/write the new field. Update DB queries.
activitiesStore.ts, activities.ts (queries)
5
Cross boundary: Layer 2 → Layer 3
Add energy_level to ActivityForm. Add to ExperienceLog.
ActivityFormScreen.tsx, ExperienceLogScreen.tsx
6
Cross boundary: Layer 3 → Layer 4
Design the energy_level UI. Add to DESIGN.md and FEATURE-SPECS.md.
DESIGN.md, FEATURE-SPECS.md, theme.ts (if new color)
7
Run sensors
Design tokens ✓, Virtual ID safety ✓, Rendering rules ✓, Seed safety ✓, Theme ↔ Spec ✓
8
Update the Change Flow Map
Add energy_level to the "IF YOU CHANGE types/index.ts" entry. Future changes know about it.

The principle

Make the
invisible
visible.

Dependencies exist whether you map them or not.
The map doesn't prevent change. It prevents surprise.

Layers tell you what's safe to change.
Flow maps tell you what connects to what.
Sensors catch what you missed.

That's the whole system.
