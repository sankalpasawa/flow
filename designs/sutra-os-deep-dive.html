The Vision

A Self-Improving Two-Way Loop

Each client company that uses Sutra makes Sutra better for ALL client companies. Network effect on organizational knowledge.

The Loop

SUTRA
Principles, OS, sensors, guidelines
↓ pushes ↓
CLIENT COMPANY
Implements. Runs. Encounters reality.
↓ feeds back ↓
SUTRA
Learns. Updates. Pushes to ALL clients.

6 Agent Types

Sutra-side

  • Publisher — pushes OS updates to all clients, adapts to each context
  • Learner — reads feedback from all clients, finds cross-company patterns
  • Researcher — studies books, frameworks, new practices continuously

Client-side

  • Executor — runs using Sutra's OS (Sense → Shape → Ship → Learn)
  • Reporter — auto-logs bugs, violations, gaps back to Sutra
  • Adapter — takes generic principles, adapts to client domain

15 Principles from 45 Sources

5 min
  • P1 INTAKE — 10 conversational questions. Extract: what, who, bet, platform, skills, 2yr vision. Output: INTAKE.md
  • P2 MARKET — Research 5-10 competitors, market size, APIs, gaps. Output: MARKET-BRIEF.md
  • P3 SHAPE — PR/FAQ test, feature carve (P0/P1/P2), risk map, success metrics. Output: PRODUCT-BRIEF.md
  • P4 DECIDE — GO / RESHAPE / KILL. Three questions: bet clear? scope small? worth time?
  • P5 ARCHITECT — Product type classification, tech stack, data model, deploy, design approach. Output: ARCHITECTURE.md
  • P6 CONFIGURE — Generate full OS: select template, replace placeholders, set metrics, set A/B config. Output: 13 files
  • P7 DEPLOY — Create company folder, register with Sutra, update Daily Pulse, deploy infrastructure
  • P8 ACTIVATE — Brief founder, select skills, start Feature #1. Company is now operating.

Gate rule: Each phase has a gate. Can't proceed to P5 without a GO in P4. Can't proceed to P6 without an Architecture Card. Phases are sequential.

Layer 2 — Scaling

Complexity Tiers — OS Scales With You

The OS is always present. The surface area changes.

Tier 1 — Personal
"Just me, just shipping"
Solo founder, 0 external users, hard deadline > perfect process.
PPR
  • Core OS only
  • Metrics: 2-3, no ship log
  • Compliance: every 3rd feature
  • Enforcement: soft (flag, don't block)
  • Skip: departments, standups, Daily Pulse
Tier 2 — Product
"Real users, real consequences"
External users depend on it. Quality matters.
DayFlow
  • Full OS minus some departments
  • Ship log required
  • Compliance: every deploy
  • A/B testing active (SUTRA vs DIRECT)
  • Security + Quality active
Tier 3 — Company
"Team, revenue, regulation"
Multiple contributors. Full accountability.
FUTURE
  • Full Sutra OS. Nothing optional.
  • All departments active
  • Hard enforcement on everything
  • Daily Pulse + Standups
  • Incident response process

Rule: Tier only goes UP, never down. Once you have external users, you don't go back to personal-tier process. Maze classified as Tier 1 at intake (0 users) but will graduate to Tier 2 when it gets external users.

Self-improvement

What Sutra Learned from Maze

11 signals captured during 15-minute onboarding. These improve Sutra for the next client.

Quality Signals

  • Rich initial description — Experienced founders front-load context. Sutra can extract multiple answers from one message.
  • Clear bet articulation — "Maze works if she comes repeatedly there." Clean, measurable, honest.
  • Instant commit — No hesitation at Phase 4. "Let's go." 3 questions are a formality when founder already knows.
  • 15 min vs 60 min target — Experienced founder + clear vision + batched questions = 4x faster.

Friction Signals

  • Wanted to batch questions — "We ask more questions together." Sequential questioning too slow for experienced founders.
  • Skipped Q5 — "I'm just creating it because I can." Not every product needs a broken market. Accept passion projects.
  • Name spelling confusion — "Maze is spelling M-A-Z-E." Sutra should confirm spelling explicitly.

Feedback Generated

Supabase org confusion — Sutra paused wrong project on wrong account. Learning: "Don't ask me anything" means product decisions, NOT destructive infrastructure actions. Verify ownership before modifying external resources.
